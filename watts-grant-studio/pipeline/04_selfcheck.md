# 04 — Self-Check: The Mandatory Pass

**This step is not optional and is not skippable under deadline pressure.**
No package leaves for `05_package.md` without clearing this gate:
**projected score ≥90% against the funder's own rubric, and zero unmet
requirements** — scored, eligibility, or attachment.

## Why this exists

A well-written application that misses a rubric criterion or an
eligibility rule scores worse than a plainly-written one that hits every
point. Reviewers score against the rubric in front of them, not against
writing quality in the abstract. This pass exists to catch the gap
between "reads well" and "scores well" before the funder does.

## Procedure

1. **Re-open the requirements matrix from `02_extract.md`.** Do not
   score from memory or from the draft alone — score row by row against
   the matrix.
2. **Score every rubric row independently**, as a reviewer would, not as
   the writer. If a rubric row is worth 15 points across 3 criteria,
   assign points per criterion, not a holistic guess.
3. **For every compliance/eligibility row**, mark Pass or Fail — no
   partial credit exists here, and a single Fail blocks delivery
   regardless of narrative score.
4. **For every attachment row**, confirm the actual file exists in the
   package draft, in the required format, correctly named — not just
   "mentioned" in the narrative.
5. **Total the scored rows** and compute the projected percentage against
   the rubric's maximum possible score.
6. **If total <90%, or any compliance/attachment row is not a Pass:**
   return to `03_draft.md`, revise the specific rows that scored low or
   failed, and re-run this entire check. Do not spot-fix only the failing
   rows without re-scoring the whole matrix — a revision to one section
   can weaken consistency (logic model vs. budget vs. narrative) that
   was previously fine.
7. **Iterate until the gate is cleared.** There is no maximum number of
   passes — the gate is the deliverable, not a target to approach.
8. **Record the final scorecard** in the package (see template below) so
   the client can see exactly how the package scores against the
   funder's own criteria before it's submitted.

## Consistency cross-checks (run every pass, not just once)

- [ ] Every number in the needs statement matches the same fact wherever
      else it's cited (program narrative, logic model, budget narrative)
- [ ] Every activity in the program narrative appears in the logic model
- [ ] Every outcome in the logic model has a matching measurement in the
      evaluation plan
- [ ] Every budget line ties to a specific activity in the program
      narrative, and vice versa — no activity without a funded resource,
      no budget line without a described activity
- [ ] Organizational capacity claims match the 990/financials in intake,
      not aspirational figures
- [ ] Every attachment listed in the compliance checklist actually exists
      in the package, in the required format
- [ ] Page/word limits are met exactly — not "close," not "over by a
      little," not "under because we ran out of things to say"
- [ ] Deadline, submission method, and file naming match the RFP exactly

## Gate

Do not proceed to `05_package.md` until GATE STATUS reads PASS on a
scorecard with a total ≥90% and every compliance and attachment row
marked Pass/Present.
